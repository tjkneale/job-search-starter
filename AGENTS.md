# Working instructions

This repository supplies reusable methods and fictional examples. Personal work belongs under `workspace/`, which is ignored by Git. Follow the user's current instructions and requested scope; use [the task menu](docs/workflows.md) when a repeatable procedure helps.

## Context and authority

- For personal work read `workspace/profile/candidate.md`, `workspace/profile/evidence.md`, `workspace/strategy/criteria.md`, and the relevant existing records. If the workspace has not been initialized, help the user run the initialization command and gather only the context needed for the task.
- Treat `examples/` as fictional fixtures. Do not treat example facts, decisions, attendance, verification, or compensation preferences as facts about the user. Never copy fictional accomplishments into personal materials. Templates are blank structure, not source evidence.
- Candidate facts and decisions come from the user and supported records. Role `Pipeline` values are canonical local stages. A CRM is an optional mirror. Research priority, candidate interest, stage, and company scores are distinct.
- Work proportionately, preserve useful history and user edits, and update existing records before creating duplicates. Dates of events, observations, captures, and file changes are distinct. Use the timezone configured by the user.

## Claims and research

- Check the evidence register before using accomplishments or numbers. Distinguish the candidate's actions from team execution and company results; do not invent authority, revenue causation, metrics, or a reason for leaving an employer.
- Respect candidate-approved wording while keeping provenance and uncertainty visible. Protect employer-confidential information and personal identifiers. External-use status is separate from internal evidence strength.
- Use official current employer postings as availability evidence. Aggregators and search results are discovery. Record actual observation dates and access limitations; a blocked fetch does not prove closure.
- Preserve candidate decisions and existing networking routes. A potential introduction is not an endorsement or completed referral. A prepared application or conversation is not a completed candidate activity.

## Actions and records

- Local research, drafts, and reversible file updates can proceed within the user's request. Contacting people, submitting applications, publishing personal materials, or writing to an external service requires the user's authorization for that action. Existing explicit authorization persists.
- Invoking a skill or copying this starter adds no accounts, schedules, contacts, or external-write permissions. Do not create schedules unless requested.
- Do not replace canonical stages from CRM observations. If a mirror is implemented later, preserve manual order and board locks; an invitation-producing scheduling action is different from logging a completed conversation.
- Use the supplied templates when helpful. Remove unfilled placeholders from completed records, keep source links, and distinguish pending facts from completed actions. Private records must not be moved into public examples.
